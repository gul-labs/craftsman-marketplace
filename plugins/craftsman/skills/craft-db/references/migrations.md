# Migrations

A migration file is a durable, auditable record of every structural change to your database. The discipline: **generate migrations from your schema tool, read every generated file before it touches any environment, and never auto-push to production.** Skipping the review step is how you ship a locking `ALTER TABLE` at 3 a.m., lose data in a botched rename, or discover that your migration tool's "push" command replayed composite foreign keys and expression indexes into a non-convergent state — again.

> **Scope split.** This file owns the generate-and-review workflow, migration naming and timestamp conventions, reversibility vs. honest forward-only, the safe-apply checklist, and the expand-contract pattern for breaking changes. It also covers the specific non-convergence issue with `drizzle-kit push`. The *schema design decisions* that precede a migration (column types, naming, FK modeling) live in `schema.md`. Multi-step large-table backfill staging — where to split the backfill work out of the schema migration — belongs in `integrity.md`. Release ordering around a separately applied Postgres migration, rollback hooks, and promotion gates belong to **`craft-infra`** → `build-release.md` and `ci-cd.md`.

## Generate, review, then apply — never skip

The generate-and-review workflow is not bureaucracy — it is the only reliable way to see what the migration tool actually decided, which is often not what you expected.

1. **Generate** the migration file from your schema tool. For Postgres, run `pnpm drizzle-kit generate` and commit both the SQL and `meta/_journal.json`. If you are reviewing another database engine, use its migration generator with a create-only mode so it writes a file without applying it.
2. **Read the entire generated file** before anything else. Confirm: the right columns are being added/dropped; no unexpected renames occurred; indexes match the intent; any generated `DOWN` block is actually safe. Tools that infer renames from column similarity can get it wrong — a missed rename becomes a data-destroying drop-then-add.
3. **Apply to a local dev database** and inspect the resulting schema. `\d tablename` (psql), `DESCRIBE tablename` (MySQL), or your ORM's introspection command. The schema should match your design exactly.
4. **Apply to a staging environment** that holds a reasonably realistic copy of the data. A migration that is trivial on an empty dev database may lock for minutes on a table with tens of millions of rows. Staging is where you find this.
5. **Apply to production** only after staging passed, with the safe-apply checklist complete (see below).

Never skip from generate directly to production. Never use "push" mode as a production workflow (see next section).

## Why ORM schema-sync / push mode is not a production workflow

ORM schema-sync commands — `drizzle-kit push`, Prisma's `db push`, TypeORM's `synchronize: true`, and any equivalent — compute the diff between your current schema definition and the live database and apply it immediately, without creating a migration file. This is convenient in early development but creates serious problems when used against real data:

- **No migration file means no review.** The diff is applied directly, regardless of which tool. You only learn what ran after the fact, from the database's own history (if you have it) or the tool's log output — not before the changes land.
- **Non-convergence on composite foreign keys and expression indexes.** As of drizzle-kit versions prior to ~0.20, this was a confirmed and documented bug: `drizzle-kit push` would drop and recreate composite foreign keys and expression indexes on every invocation, even when the schema was unchanged. Verify against the version in use; the structural risk of no migration file remains regardless. On a live table, this kind of non-convergence causes unnecessary lock activity and can briefly violate referential integrity. A migration file generated by `drizzle-kit generate` produces stable SQL that does not re-run these destructive operations.
- **Irreversible in practice.** Because there is no SQL file, there is nothing concrete to roll back to, diff against, or include in a deployment artifact. Rollback becomes "push the previous schema definition" — which runs another diff, possibly missing intermediate states.

Use `drizzle-kit push` for local throwaway development databases only. For every other environment, use `drizzle-kit generate` and apply the resulting SQL file through a controlled migration runner. The same constraint applies to every push-flavored command: they all share the structural risk of skipping review and producing no auditable artifact.

## Naming and timestamp conventions

Discover the naming pattern already established in the repo's migration directory before generating anything. If none exists yet, establish a consistent standard and document it.

**Recommended pattern:**

```
<timestamp>_<short_description>.<ext>
```

Examples:
```
20240315120000_add_workspace_invites_table.sql
20240316083000_add_idx_invites_workspace_id.sql
20240317140000_drop_legacy_invite_token_column.sql
```

Rules:
- **Timestamp first, UTC, to the second** (`YYYYMMDDHHmmss`). This makes the execution order sortable and human-readable — collisions at the same second require manual disambiguation (increment one timestamp by a second) or use a sequence-based scheme. No dependency on the migration runner's stored sequence table to understand the order.
- **Descriptive slug, not a ticket number.** `add_workspace_invites_table` tells a reviewer what the file does without opening it. `PROJ-1234` tells them nothing. Ticket references belong in a comment inside the file, not the filename.
- **One logical change per file.** A file that adds a table, backfills a column, and drops an index in sequence is hard to review, hard to bisect, and impossible to roll back partially. Keep the unit small.
- **Never rename a migration file after it has been applied anywhere.** Migration runners key on the filename (or a hash of it) to determine what has run. Renaming an applied file will cause the runner to attempt to re-apply it, or throw a state mismatch, depending on the tool.

## Reversible vs. honest forward-only

The goal is not to make every migration reversible — it is to be honest about which are and ensure the reversible ones actually work.

**Reversible migrations** are worth the cost when:
- The change is structural but data-preserving (add a nullable column, add an index, add a constraint, create a table). The `DOWN` block is trivially safe.
- The rollback is a realistic recovery path. A migration applied to production at 14:00 that needs to be reversed by 14:05 because a deploy went wrong — the `DOWN` block has to work on real data, not just empty test fixtures.

**Forward-only is the honest choice when:**
- The migration drops a column or table. Even if you write a `DOWN` that recreates the column, you cannot restore the data you dropped. The `DOWN` is theater. Declare it explicitly:
  ```sql
  -- DOWN: intentionally omitted — column data is not recoverable after this runs.
  --       If rollback is needed, restore from backup.
  ```
- The migration renames a column (the expand-contract pattern is the right tool; see below). A rename `DOWN` that renames back will break any code that already started using the new name.
- The `DOWN` block would itself require a long lock or batch process to be safe. A reverse that is as risky as the forward migration is not a meaningful safety net.

**Test the `DOWN` block.** If you write a reversible migration, apply the `UP`, run the app's test suite against the migrated schema, then run the `DOWN` and confirm the schema is back to what it was. A `DOWN` you have never run is not a rollback — it's speculation. Track down-tested migrations as part of the PR checklist.

## Safe-apply checklist

Work through this before running any migration against staging or production.

**Before applying:**
- [ ] Read the generated SQL in full. No surprises.
- [ ] Does any step hold a full-table lock? In PostgreSQL: `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT …` before Postgres 11, or in any Postgres version when using a volatile default expression (e.g. `clock_timestamp()`, `gen_random_uuid()`). Note: `NOW()` / `transaction_timestamp()` is *stable* (not volatile) and does not trigger a rewrite; `clock_timestamp()` is volatile because it returns a different value on every call. PG11+ optimized this only for non-volatile constant defaults. Also: most `ALTER TABLE` forms take an `AccessExclusiveLock` and block all concurrent reads and writes for their duration — there is no `CONCURRENTLY` equivalent for `ALTER TABLE` itself. Many index additions also lock. Check the Postgres version.
- [ ] Any `CREATE INDEX` on a large table must use `CREATE INDEX CONCURRENTLY` (Postgres) or an equivalent non-blocking form. Standard index creation takes a `ShareLock` for its entire duration, blocking all DML (writes) but still allowing reads. On a busy write-heavy table this effectively causes write unavailability for the lock duration.
- [ ] Does any step touch a column that a hot query path reads or writes on every request? If so, assess the lock duration against acceptable downtime.
- [ ] Are there any FK constraints being added without an existing covering index on the referencing (child) column? A missing index on the child FK column becomes a sequential scan when the parent row is deleted or updated with ON DELETE/UPDATE CASCADE/RESTRICT, and degrades JOIN performance. Add an index on the child FK column before or alongside the constraint.
- [ ] For large-table operations: is the table too large for an in-migration backfill? If so, split the backfill into a separate step — see `integrity.md` for the staging pattern.
- [ ] Is there a backup or point-in-time recovery checkpoint you can roll back to if the migration must be aborted partway?

**During apply:**
- [ ] Watch the query lock wait list (`pg_stat_activity` / `SHOW PROCESSLIST` / your monitoring tool). A migration that enters a queue behind a long-running transaction will hold every subsequent query.
- [ ] For migrations on large tables: monitor table bloat and replication lag. Long-running DDL can spike lag on read replicas.

**After apply:**
- [ ] Inspect the actual schema (`\d+`, ORM introspection, or your schema-dump tool). Confirm it matches the intent exactly.
- [ ] Run smoke tests or the staging test suite against the migrated schema.
- [ ] Confirm the migration runner recorded this migration as applied in its own state table (and in your deployment log — see `craft-infra → build-release.md`).

## Where and how migrations connect

The migration *file* can be perfect and still fail, or hurt production,
because of how the runner connects. The adopted Postgres profile's rules are in
`postgres-standard.md` §6; check these mechanics alongside the SQL:

- **A direct or session connection, never the transaction pooler.** DDL,
  migration-runner advisory locks, `SET` for the session and non-transactional
  steps all need one real session. Use a separate env var (e.g.
  `DATABASE_URL_DIRECT`) and make the runner refuse the transaction-pooler
  endpoint, failing closed rather than rewriting the port. See
  `connection-pooling.md` → "Connection targets".
- **Its own role, with its own timeouts.** Runtime roles carry short
  `statement_timeout` defaults (`connection-pooling.md` → "Timeouts and
  roles"). The migration runner logs in as the owner/migration role and sets
  its session limits *before* `BEGIN`:
  ```sql
  SET statement_timeout = 0;      -- or an explicit ceiling for this migration
  SET lock_timeout = '10s';       -- fail fast instead of queueing behind traffic
  ```
  If runtime and migrations still share one role, this override is
  mandatory, and the runner's test must assert it. Otherwise the first long
  migration is killed halfway by the app's 15 s timeout.
- **Run by a person or a manually dispatched workflow.** Apply to staging first. Never inside the platform
  build (a serverless build command that migrates production on every
  deploy), never at app or worker boot, never from ordinary CI.
- **Push stays local.** `drizzle-kit push` (or equivalent) is guarded to
  loopback URLs in the script that wraps it.
- **Non-transactional steps are registered, not dodged.** If the runner wraps
  each file in a transaction, `CREATE INDEX CONCURRENTLY` goes in a registered
  step the runner executes outside a transaction. Tests run the same chain;
  they never strip `CONCURRENTLY` to make it pass.
- **Drift is checked on every commit.** Regenerating from the schema must
  produce no new migration (for drizzle: run `drizzle-kit generate` in CI and
  fail on any diff), and a journal test confirms every file on disk is in
  the journal and vice versa.

## Expand-contract for breaking changes

A "breaking" schema change is one where the old application binary is incompatible with the new schema, or vice versa. The canonical examples: renaming a column, changing a column's type in a way the old code cannot read, splitting a table. Doing any of these in a single migration with a deploy-then-run order causes downtime — the window between the migration running and the app binary restarting has one of them out of sync.

The expand-contract pattern avoids this by making the change across multiple migrations and deploys, each of which leaves the database in a state that is simultaneously compatible with the old and new application code:

**Example: rename `user.email_address` to `user.email`**

1. **Expand** — add the new column `email` as nullable, alongside the old `email_address`. Deploy app code that writes to *both* columns and reads from whichever is non-null (or `email` with a fallback).
   ```sql
   ALTER TABLE users ADD COLUMN email TEXT;
   ```
2. **Backfill** — populate `email` from `email_address` for all existing rows, in batches (see `integrity.md`). The app is still writing both columns, so no reads fail.
   ```sql
   -- PostgreSQL does not support UPDATE ... LIMIT directly.
   -- Run this in a loop until 0 rows are affected:
   UPDATE users SET email = email_address
   WHERE id IN (SELECT id FROM users WHERE email IS NULL ORDER BY id LIMIT 5000);
   ```
3. **Index** — create the index in its own migration file, before adding constraints on the column. `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block; if your migration runner wraps files in transactions by default (Flyway, golang-migrate, and many others do), this file must be configured for non-transactional mode.
   ```sql
   -- This file must run outside a transaction block:
   CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
   ```
   If the runner has no per-file non-transactional mode, extend the real `db:migrate` runner
   with a registered `manual/` step and applied-log before using `CONCURRENTLY`. A plain
   (non-CONCURRENTLY) `CREATE INDEX` is an alternative only in a scheduled maintenance window
   where its write lock is acceptable; keep it in the registered migration chain and document
   the lock implications. Do not run untracked `psql` outside the runner.
4. **Constrain (NOT NULL)** — once all rows have `email` populated, add the NOT NULL constraint.
   ```sql
   ALTER TABLE users ALTER COLUMN email SET NOT NULL;
   ```
   > **Large tables:** direct `SET NOT NULL` takes an `ACCESS EXCLUSIVE` lock *and* performs a full table scan to verify no nulls exist — this can block reads and writes for the entire scan duration. Avoid it on large tables. Instead: (1) `ALTER TABLE users ADD CONSTRAINT email_not_null CHECK (email IS NOT NULL) NOT VALID;` — this skips checking existing rows, so it is fast. (2) In a separate migration, `ALTER TABLE users VALIDATE CONSTRAINT email_not_null;` — this holds only a `SHARE UPDATE EXCLUSIVE` lock (non-blocking for reads and normal DML) while scanning. (3) Once the check constraint is validated, `ALTER TABLE users ALTER COLUMN email SET NOT NULL;` — Postgres recognises the valid check and skips the full scan, taking only a brief `ACCESS EXCLUSIVE` lock. This staged approach avoids the long blocking window of the direct `SET NOT NULL`.
5. **Contract** — deploy app code that reads and writes only `email`. Then drop `email_address`.
   ```sql
   ALTER TABLE users DROP COLUMN email_address;
   ```

Each of these steps is a separate migration file and a separate deploy. The risk window between steps is ordinary rolling-deploy risk, not a hard data-availability gap. The cost is calendar time; the benefit is zero-downtime and full rollback at every step until the final drop. For the deploy ordering (migration before or after the binary restart, rollback hooks), see `craft-infra → build-release.md`.

Apply the same pattern to column-type changes (add the new-type column, dual-write, backfill, swap, drop) and table splits (add the new table, dual-write, backfill FK references, swap reads, drop the old table). The shape is always: new thing alongside old → dual-write period → backfill → swap → cleanup.

## Quick-reject checklist

Flag with `file:line` and the fix:

| Pattern | Fix |
| --- | --- |
| Migration applied via ORM schema-sync / push mode (`drizzle-kit push`, `db push`, `synchronize: true`, or equivalent) to a non-loopback database | Generate a migration file; apply via the migration runner; never push outside loopback |
| Generated migration file unread before first apply | Read the full SQL before any `migrate up`; reject the PR if the reviewer cannot confirm this was done |
| `CREATE INDEX` without `CONCURRENTLY` on a live large table and no approved lock window | Use registered `CREATE INDEX CONCURRENTLY`; it must run outside a transaction block |
| `ALTER TABLE … ADD COLUMN … NOT NULL` with a constant default on Postgres < 11 | Add as nullable, backfill, then `SET NOT NULL` in separate steps |
| Multi-step data change (backfill) inside a schema migration | Split the backfill into its own migration or script; see `integrity.md` |
| Column rename done as a single drop-add migration | Use expand-contract: add new, dual-write, backfill, drop old, across multiple deploys |
| `DOWN` block that does not actually restore data (drop → recreate) | Mark as forward-only with an explicit comment; remove false safety net |
| `DOWN` block written but never executed against a real database | Test the `DOWN` in the PR; an untested rollback is not a rollback |
| Migration filename renamed after it has been applied | Never rename; create a corrective migration instead if the intent is wrong |
| Migration bundles multiple unrelated changes in one file | One logical change per file; separate timestamps, separate review |
| No staging apply before production | Always apply to staging first; large-table locks only appear at scale |
| FK added to a column with no covering index on the referencing side | Add an index on the FK column before or alongside the constraint |
| Migrations applied through the transaction-mode pooler URL | Use a direct/session URL; the runner refuses the pooler endpoint |
| Migrations run in the platform build or at app/worker boot | A manual or dispatched step, staging first |
| Runner shares the runtime role and doesn't set `statement_timeout`/`lock_timeout` before `BEGIN` | A separate migration role, or a mandatory, tested session override |
| No drift check in CI (schema changes without a migration can merge) | Regenerate in CI and fail on a diff; add a journal test |
| Test harness rewrites migration SQL (e.g. strips `CONCURRENTLY`) to apply it | Register non-transactional steps; test the exact chain with the real runner |
